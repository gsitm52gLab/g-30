# GS HALE 구현·독립 검증·보완을 반복하는 에이전트 실행 규약

문서 상태: 실행 설계 / 2026-09-21. 기준은 `리테일_운영플랫폼_최종통합_상세기획_v3_검토용.md` 15~19절의 A01~A26, 개발 순서, 제외 범위와 자료 공백이다. 이 문서는 구현·테스트·실호출 완료 증거가 아니다. 최신 작업 상태는 사용자가 Git과 origin 연결을 준비한 `main`의 초기 commit 전 상태다. 환경설정 외 제품 코드는 아직 준비되지 않았으며 기존 설정·변경을 보존한다. 다른 프로젝트의 과거 build·테스트 성공을 이 프로젝트의 결과로 가져오지 않는다. 사용자의 10분은 이번 설계 문서 작성 목표이며 전체 제품 완성 시간의 약속이 아니다.

아래 세션·패킷·상태 관리 방식은 **프로젝트가 지켜야 할 운영 규약**이다. 특정 앱이 영구 실행, 자동 재개, 세션 JSONL 내보내기 등을 제공한다고 가정하지 않는다. 실행 시작 때 실제 사용 가능한 도구를 확인하고, 없는 기능은 구현할 실행기 또는 명시적 제약으로 기록한다. 독립 세션 실행 도구가 없으면 자체 검토만 진행할 수 있으며 ‘독립 검증 완료’로 바꾸지 않는다.

실행 목표를 활성화할 때는 단일 활성 Goal 아래 G00~G18을 체크포인트로 관리한다. 19개의 Goal을 동시에 생성하는 방식이 아니다. 이 문서의 B0~B7은 작업 의존성 묶음이고 G 체크포인트 및 원문의 A 수용 기준과 별도로 매핑한다.

실행 상태의 단일 원장은 `.execution/run-plan.json`이다. `docs/execution-v1/04-run-plan.json`은 초기 계획 원본이며 실행 중 상태와 구분한다. 각 명령은 배정된 구현/검증 worktree의 실제 절대경로에서 실행하고 그 cwd를 증거에 남긴다. 논리적 대상 저장소가 GS HALE이라는 이유로 모든 검사를 원본 루트에서 실행하지 않는다.

## 1. 역할과 동시 실행

메인 포함 최대 4개 세션만 실행한다. 일반 배치는 메인 1 + 구현 2 + 검증 1이며, 기반 작업이나 최종 통합 때는 구현 수를 줄인다. 실행 슬롯은 고정 신분이 아니지만 **어떤 후보의 구현자와 검증자는 서로 다른 세션 ID**여야 한다. 구현자의 수정 이력이 있는 후보를 그 세션이 검증하지 않는다.

| 역할 | 책임 | 변경 권한 |
| --- | --- | --- |
| 메인 오케스트레이터 | 요구 추적, DAG·자원 예약, 작업 발행, 결과 수신, 증거 확인, 통합, 회귀·누락 감사, 최종 보고 | 작업 원장·통합 브랜치·승인된 공통 파일 |
| 구현 서브세션 | 배정 범위 구현, 자체 점검, 후보 commit과 변경 설명 제출 | 배정 worktree의 소유 파일만 |
| 독립 검증 서브세션 | 명세에서 기대값 도출, 고정 후보에서 실제 실행, 부정 시나리오·회귀 검사, 결함 패킷 작성 | 후보 코드는 수정 금지; 별도 증거 폴더만 쓰기 |
| 보완 서브세션 | 결함 재현·원인 수정, 영향 범위 갱신, 새 후보 제출 | 재배정 받은 파일; 이전 검증 판정 변경 금지 |

무인 진행은 허용된 로컬 구현·검증·수정·통합을 매 단계 재질문 없이 계속하는 방식이다. 실데이터 외부 전송, 운영 배포, 실제 메일 발송 등 별도 권한이 필요한 작업은 자동 확장하지 않는다. 외부 의존이 막힌 동안 독립적인 로컬 작업을 계속하고 마지막에 정확한 미완료 목록을 남긴다. 기능을 조용히 빼거나 검증기를 약화해 종료시키지 않는다.

사용자가 제공한 환경설정 사용과 OpenAI 금액 상한 해제를 지시한 범위에 따라, 실제 Goal 실행에는 설정된 OpenAI로 합성/허용 공개 데이터의 최소 실호출 검증을 포함한다. 키가 이미 설정됐다면 같은 사용 권한을 반복 질문하지 않는다. `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL`은 런타임에 로드하며 비밀값은 문서·패킷·로그에 복사하지 않는다. 모델은 정상 환경변수 파서로 주석 등을 처리한 최종 설정을 확인하며, G00에서 공백이 들어간 모델 표기를 동일 모델의 API 식별자 `gpt-6-astra`로 정규화한다. 계정 변경·추가 결제·실데이터 외부 전송은 이 허용 범위에 포함하지 않는다. 이번 문서 작성에서는 실호출하지 않았다.

## 2. 착수 조건과 실행 공간

현재 단계에서는 아래 절차를 실행하지 않는다. 구현 착수 시 메인이 기존 파일 목록·사용자 변경·사용 가능한 도구를 확인한 뒤 적용한다.

1. 이미 준비된 Git과 origin을 재설정하지 않는다. `.gitignore`에 `.env*`, `*.env`, `gs-hale.env`, 로컬 DB, 업로드, 민감 로그를 제외한다. 환경파일이 stage에 있으면 index에서만 제외하고 원본은 보존한다. 비밀값을 출력하지 않고 추적 여부와 경로만 확인한다. 초기 commit은 검토한 경로만 명시적으로 추가하며 `git add .`로 환경파일을 포함시키지 않는다. 별도 지시 없이 원격 push하지 않는다.
2. 기반 scaffold·의존성 lockfile·실행 명령·합성 fixture를 만든다. 이 결과를 독립 검증한 commit이 모든 분기의 기준선이다. 명령이 아직 존재하지 않으면 `NOT_RUN`이며 가상의 실행 결과를 만들지 않는다.
3. 실행 ID별 통합 브랜치와 작업별 Git worktree를 만든다. 예: `runs/<run-id>/T010/impl`, `runs/<run-id>/T010/verify`. 검증 worktree는 정확한 후보 SHA에 detached checkout한다. 경로·브랜치·기준 SHA를 원장에 저장한다.
4. 슬롯별 포트는 예약 원장으로 할당한다. 예를 들어 4101~4103은 최초 후보일 뿐이며 실제 사용 중이면 빈 포트를 다시 예약한다. 테스트는 할당받은 base URL만 사용하고 서버 PID·시작/종료 시간을 남긴다.
5. SQLite는 작업·시도별 다른 DB 파일을 사용한다. 서버형 DB를 선택하면 별도 데이터베이스/스키마·접속권한으로 격리한다. 파일 저장소 prefix, 쿠키 이름, 인증 테스트 계정, 큐 namespace도 분리한다. 검증자는 새 DB에 migrate/seed한 뒤 실행하며 구현 DB를 재사용하지 않는다.
6. 비밀설정은 저장소 밖에서 필요한 실행에만 주입한다. 검증 산출물에는 변수 이름과 설정 유무만 기록하고 값·인증 헤더·쿠키·DSN을 남기지 않는다. seed·업로드·AI 입력은 합성 자료만 사용한다.

다른 세션의 서버 종료, 전체 DB 삭제, 포트 점유 해제를 위한 무차별 프로세스 종료를 금지한다. 정리는 자신이 예약한 자원과 확인한 PID만 대상으로 한다. 시작 전·완료 후 Git 상태를 기록해 배정 밖 파일 변경을 검출한다.

## 3. DAG와 파일 소유권

원문의 단계는 기능 삭제가 아닌 순서다. 메인은 A01~A26 각각을 작업, 테스트, 증거와 연결하는 추적표를 만든다. 독립성이 확인된 작업만 병렬화하며 의존성의 ‘문서 작성 완료’를 ‘실행 가능한 계약 완료’로 취급하지 않는다.

| 작업 묶음 | 선행 조건 | 주요 수용 기준 |
| --- | --- | --- |
| B0 기반·DB·fixture·실행기 | 없음 | A25 기반 부분 |
| B1 컨텍스트·회원·서버 권한 | B0 검증·통합 | A01~A02, A19 |
| B2 업무·요청·제출·보완·수동 완료 | B1 및 공통 스키마 확정 | A03~A07, A14, A20 |
| B3 상품·자료·표준 Excel | B1 및 상품/파일 계약 | A10~A12 |
| B4 공지·문의·팝업·알림·검색 | B1, 업무/이벤트 계약 | A08~A09, A13, A18 |
| B5 PR·실물·일정·외부 대기 | B2와 상품/알림 연결 계약 | A15~A17 |
| B6 일본 일반 화장품 AI 수직 기능 | B1, 파일·버전·권한 계약 | A21~A23 및 13개 AI 평가 |
| B7 최종 통합·접근성·모바일·재현 | B2~B6 통합 | A01~A25 전체, A26 별도 상태 |

API DTO·스키마·migration·권한 공통 함수·lockfile·루트 설정은 한 번에 한 소유자만 편집한다. 공유 파일 변경이 필요하면 구현자는 dependency 요청을 제출하고, 메인이 기존 lease 해제 후 소유권을 재배정한다. DB migration은 생성 순서와 통합 순서를 직렬화한다. 파일 glob의 겹침도 충돌로 취급하며 경로를 나눌 수 없으면 병렬 실행하지 않는다.

초기 단계가 후행 기능 전체의 검증을 요구하는 순환을 만들지 않는다. G00은 최소 저장 adapter의 합성 레코드 왕복·재시작과 설치/실행 기반을 검증하고, G02는 정책 harness와 당시 존재하는 경로를 검증해 선행 승인을 얻는다. 이후 생성되는 업무·상품·문의·파일·AI API의 영속성/권한 검사는 각 모듈 DoD에 추가하고 G18에서 전체 행렬을 회귀한다. 없는 후행 기능을 G00/G02에서 통과로 기록하지 않으며 해당 검사를 삭제하지도 않는다.

계약 변경은 버전을 올리고 영향 소비 작업을 `STALE`로 표시한다. 이미 통과한 후보라도 기준 계약이 바뀌면 관련 검증을 다시 실행한다. 다른 worktree의 미완성 파일을 직접 가져오거나 검증되지 않은 후보를 몰래 선행 의존성으로 사용하지 않는다.

## 4. DoR·상태 전이·DoD

**착수 가능(DoR):** 원문 요구/A 번호, 목표 행동과 금지 행동, 선행 통합 SHA, 소유 경로, 합성 fixture, 기대 결과, 실제 실행할 검사 명령, 자원 배정, 외부 의존의 검사 수준이 모두 패킷에 있어야 한다. 누락되면 메인이 보완하고 `READY`로 옮긴다. 큰 업무는 UI·API·영속성을 함께 확인할 수 있는 작은 수직 작업으로 분할한다.

정상 전이는 `PLANNED → READY → IMPLEMENTING → CANDIDATE → VERIFYING → VERIFIED → INTEGRATING → REGRESSION → ACCEPTED`다. 다음 예외 전이를 별도로 둔다.

- 실행 가능한 결함: `VERIFYING/REGRESSION → NEEDS_FIX → IMPLEMENTING`. 새 commit·시도 번호를 발행하고 원 결함 테스트와 영향 회귀를 다시 실행한다.
- 도구·자원 실패: `… → RETRY_WAIT`; 기능 실패와 구분하여 같은 후보를 새 깨끗한 환경에서 재시도한다.
- 선행 변경: `… → STALE → READY`; 새 기준으로 재배정하며 이전 PASS는 역사로만 보존한다.
- 외부 자료·권한 부재: `… → BLOCKED_EXTERNAL`; 막힌 범위와 재개 조건을 기록하고 다른 READY 작업을 계속한다.
- 실행 중단: `… → INTERRUPTED`; 완료로 바꾸지 않고 checkpoint에서 복원한다. `CANCELLED`는 사용자의 취소 또는 명시적 범위 변경에만 사용한다.

이 상태들은 프로젝트 작업 원장의 상태이며 앱의 Goal 상태 API와 동일하다고 가정하지 않는다. 전이마다 시각, 작성 세션, 사유, 후보 SHA, 이전 상태 버전, evidence 참조를 append-only 이벤트로 남긴다. 메인만 상태를 확정하고 compare-and-swap 방식으로 이전 버전을 확인해 중복 전이를 막는다.

**작업 완료(DoD):** 요구 행동이 UI·서버·저장 데이터에서 일치하고, 권한/실패/동시성 검사와 관련 회귀가 통과하며, 독립 검증 증거를 메인이 확인하고 통합 SHA에서 재검증해야 `ACCEPTED`다. 스크린샷만 있는 경우는 UI 관찰 증거이며 서버 권한·DB 영속성의 대체물이 아니다. 알려진 결함, 누락 검증, 재현 명령도 함께 남긴다.

## 5. 결과 수신과 독립 검증 루프

구현자는 작업 완료를 선언하는 대신 후보 SHA, diff 목록, 자체 검사 결과, 알려진 한계를 제출한다. 메인은 소유권 위반·미커밋 변경·기준선 불일치를 확인한 후 후보를 고정한다. 후보를 고친 순간 새로운 SHA가 필요하며 기존 검증 결과는 승계하지 않는다.

검증자는 구현자의 설명과 별도로 원문 수용 기준을 읽고 성공·실패 기대값을 만든다. 정확히 같은 SHA를 새 worktree/DB에서 실행하고 실행 전후 SHA·Git 상태·환경 지문을 기록한다. 다른 컨텍스트 ID 접근, 가격 누출, 중복 제출, 재로그인 후 영속성, GSG의 잔여 항목을 남긴 수동 완료 등 실패하기 쉬운 경계를 확인한다. 테스트가 존재한다는 사실, mock 화면, 테스트 수 0, 전부 skip, 빌드만 성공한 결과는 시나리오 통과가 아니다.

검증 실패 시 패킷에는 재현 순서, 기대/실제 결과, 심각도, A 번호, 로그 위치, 수정 후 재실행 목록을 넣는다. 검증자는 코드를 수정하지 않는다. 구현자에게 보완을 맡긴 뒤 다른 검증 세션이 새 후보를 확인한다. 같은 사람이 수행한 자체 점검은 계속 유용하지만 독립 판정 칸에는 적지 않는다.

메인은 `PASS` 문자열을 신뢰해 통합하지 않는다. 후보 SHA 일치, 검증자 독립성, 실행 명령과 실제 종료코드, 보고서 파일 존재·해시·테스트 개수·실패/skip, A 번호별 assertion과 증거를 대조한다. 패킷의 숫자만 보지 않고 실행 도구의 반환과 실제 보고서를 확인한다. 위험한 권한·영속성 검사는 메인 또는 별도 검증 실행에서 재현한다. 검증 스크립트 자체가 삭제·완화됐는지도 diff로 확인한다.

통합은 메인 한 곳에서 직렬 실행한다. 충돌을 해결한 내용도 새로운 구현 변경이다. 통합 commit을 고정한 뒤 별도의 깨끗한 공간에서 핵심 여정과 영향 범위 회귀를 실행한다. 통합자가 수정한 코드의 최종 독립 검증은 다른 세션이 맡는다. 통합 회귀 실패 시 원 후보의 성공을 근거로 무시하지 않고 수정 작업을 발행하며, 마지막 검증 통과 기준선을 유지한다.

## 6. 서비스별 검증 수준과 완료 표현

선택한 공급자·구현 방식은 착수 패킷에 확정한다. 환경파일이 있다는 사실은 서비스 연결 성공의 증거가 아니다.

| 대상 | local/mock | integration | operational gate |
| --- | --- | --- | --- |
| 인증·회원 | 합성 계정·초대 링크 흐름 | 실제 선택 인증 방식, 서버 세션·중지·멤버십 격리 | 운영 계정/도메인·복구·권한 책임 확인 |
| DB | 메모리/fixture 동작 | 선택 DB migrate/seed·쓰기·재시작 영속성·동시성 | 운영 백업 실제 복원·보존/삭제 정책 |
| 파일 | 합성 파일·로컬 저장 | 선택 저장소 업로드/다운로드·권한·버전·크기 제한 | 운영 접근 정책·용량·복구·악성 파일 대응 |
| 메일·알림 | 앱 알림·메일 sink·초대 링크 복사 | 허가된 테스트 수신처의 실제 전달·중복 방지 | 운영 도메인/반송/실수신 정책; 실제 발송 권한 |
| 대화·실시간 | 단일 세션 fixture | 두 세션 실제 이벤트·연결 끊김·누락 복구 | 배포 환경의 연결 유지·관측·장애 대응 |
| OpenAI·OCR·corpus | 합성 응답과 timeout/429/키 없음 | 허가된 합성 입력의 실제 호출, 읽은 범위·locator·버전·비용 기록 | 근거 corpus 확정·사람 평가·운영 접근/보존 정책 |
| Excel | 표준 합성 양식 정상/오류/가격 권한 | 구현 parser·DB 반영·내보내기 검증 | 현업 원본 한 종류 확보 후 실제 매핑 확인 |
| 배포·관측 | 로컬 build·실행 | 별도 테스트 환경 smoke·오류 관측 | 운영 배포/공개 권한·복구·인계 확인 |

각 칸은 `PASS / FAIL / NOT_RUN / BLOCKED / N/A(사유)`로 따로 보고한다. A01~A25 필수 흐름이 남으면 전체 구현 완료로 표현하지 않는다. **G17은 합성/오류 주입 검사와 설정된 OpenAI의 허용 입력 실제 호출 성공 증거가 모두 있어야 ACCEPTED다. G17 미실행·실패이면 전체 Goal 완료 불가다.** 실호출 성공에는 실제 모델·실행 ID·시각·schema/근거 연결·usage의 비밀값 제거된 증거를 연결한다. 실제 메일·현업 Excel·전문가 검수·운영 백업 복구는 미확보 시 별도 운영 한계로 표시할 수 있으며 G17 실호출과 같은 선택 항목으로 묶지 않는다. 필수 제품·OpenAI 연동이 통과하고 운영 항목이 남으면 ‘제품·명시된 연동 검증 완료, 운영 항목 미검증’처럼 범위를 한정한다. 합성 AI 평가의 통과로 법률 적합성이나 실사용 정확도를 확정하지 않는다.

## 7. 증거 보존과 최종 누락 감사

증거의 표준 비공개 경로는 프로젝트의 `.execution/private/runs/<run-id>/<Gxx>/<attempt>/`다. Git 추적에서 제외하며 worktree별로 분산된 증거는 이 위치에 수집한다. 여기에 task/result JSON, 원장 이벤트, 변경 diff, 명령·작업 디렉터리·시작/종료·종료코드, stdout/stderr, 테스트 보고서·스크린샷·trace, commit과 lockfile hash, fixture 버전, 산출물 SHA-256 목록을 보존한다. manifest에는 각 증거의 실제 절대경로와 hash를 기록한다. 공유 문서에는 비식별 요약과 증거 참조만 둔다. 메인의 판정도 증거 참조를 가진 별도 파일로 남기며 수정 시 원본을 덮어쓰지 않는다.

실제 세션 JSONL에 접근할 수 있으면 해당 실행 구간의 원본 경로·세션 ID·해시를 증거 manifest에 기록하고 비공개 위치에 보존한다. 원본은 공개 저장소에 넣지 않으며 공유본은 비밀값·개인정보를 제거한 파생본임을 표시한다. **접근 불가하면 `session_log_status: unavailable`과 이유를 남긴다. 요약문이나 메인이 만든 이벤트 JSONL을 실제 세션 JSONL이라고 부르지 않는다.** 실행기 로그와 테스트 산출물로 확인 가능한 범위만 판정한다. 비밀값을 transcript에 출력하게 하는 명령은 처음부터 실행하지 않는다.

최종 감사는 기능 목록에서 테스트를 찾는 방향과 테스트에서 원 요구를 찾는 방향을 모두 수행한다. A01~A26, AI 13개 평가, 필수 화면·오류 상태, 제외/보류 범위, 현업 자료 공백을 대조해 각 항목에 통합 SHA·검증 수준·증거·미완료 사유가 있는지 확인한다. A 번호가 한 번 등장했다는 이유로 세부 조건 전체를 커버했다고 처리하지 않는다. 독립 상품 메뉴, 사용자 단위 할당, 줄글 버전, 문의 팝업, 가격 권한, GSG 수동 완료가 빠지지 않았는지 별도로 확인한다.

최종 보고에는 승인된 범위, 통합 SHA, 통과/실패/미실행 수, 실제 실행 명령, 운영 게이트, 알려진 결함, 다음 재개 작업과 산출물 경로를 남긴다. 전체 결과를 작성한 메인 외 세션이 추적표·증거 누락을 마지막으로 감사한다. 가능하지 않으면 ‘독립 최종 감사 미수행’으로 남긴다.

## 9. 재시도·재개 규칙과 가짜 검증 방지

- 메인은 작업 ID·시도·lease 소유자·만료 시각을 관리한다. 동일 idempotency key의 완료 패킷은 한 번만 수신 처리한다. 늦게 도착한 결과는 보존하되 현재 시도나 후보와 다르면 채택하지 않는다.
- 일시적 도구/네트워크 실패는 동일 원인에 자동 재시도 최대 2회, 지수 backoff와 오류 분류를 적용한다. 실패한 기능 테스트를 재실행만 하여 성공할 때까지 숨기지 않는다. flaky 의심은 양쪽 결과를 보존하고 원인 수정 전 통과로 확정하지 않는다.
- 동일 결함에 보완 3회 실패하면 메인이 요구·계약·재현을 재진단하고 더 작은 작업 또는 다른 구현 세션으로 재배정한다. 범위 삭제·테스트 삭제·무제한 동일 재시도는 하지 않는다. 외부 조건이 필요한 경우만 해당 항목을 차단 상태로 둔다.
- checkpoint는 마지막 통합 검증 SHA, DAG 상태 버전, 실행 중 task/attempt/session, 후보 SHA, 패킷·manifest hash, 자원 lease, 미수신 결과, 결함·외부 차단, 다음 READY 작업을 포함한다. 파일은 임시 파일 작성 후 원자 교체하고 이전 버전도 보존한다.
- 재개 시 세션·프로세스가 살아 있는지 먼저 확인해 중복 실행을 막는다. 접근 불가 세션을 완료로 추정하지 않는다. worktree SHA·dirty 상태·DB·증거 hash를 대조하고, 중간까지 실행된 검사는 깨끗한 자원에서 다시 수행한다. 외부 호출은 제공자 요청 ID·멱등성 지원을 확인하기 전 무조건 재전송하지 않는다.
- 통합 SHA가 달라졌거나 검증 후 코드가 바뀌었으면 이전 PASS는 재사용하지 않는다. 중단된 후보는 새 시도에서 재검증하고 마지막 통과 기준선에서 통합을 이어간다. 손실된 증거는 복구하거나 다시 실행하며 기억으로 로그를 복원하지 않는다.

최종 판정 전 체크: □ 구현자와 검증자 ID가 다른가 □ 동일 후보 SHA인가 □ 실제 명령과 종료코드가 있는가 □ 보고서가 존재하고 hash가 맞는가 □ 필요한 assertion을 실제 실행했는가 □ skip·0 tests를 성공으로 세지 않았는가 □ 통합 후 회귀를 수행했는가 □ mock/실호출/운영 검증을 구분했는가 □ 실제 세션 JSONL 부재를 정직하게 표시했는가 □ 필수 누락과 외부 차단을 최종 보고에 남겼는가. 하나라도 확인되지 않으면 해당 범위를 검증 완료로 표시하지 않는다.
