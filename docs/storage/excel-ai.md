# Excel and AI private Storage consumers

Supabase mode uses metadata-only upload grants for Excel sources and AI assets. The browser uploads bytes directly; the service rechecks current actor/context/visibility, file signature and SHA, then commits the feature record, command receipt, and exact audit references in the grant's transaction. Legacy multipart endpoints reject Supabase requests before reading file bodies. Mock and SQLite keep their existing local behavior. Missing remote configuration or legacy rows without a remote backend never fall back to disk.

Excel source bytes remain immutable Storage objects. Parsed workbooks and preview plans remain private `importStage` JSONB strings with their own hash: source 24 hours, preview 30 minutes, 64MiB payload, 50 active stages per actor. Reads check current actor/context and internal-price permission. Apply consumes its preview in the same transaction as every product/version/price/event/audit/receipt mutation. A committed batch can still replay after staging expires. CAS, all-row validation, leading zeros, exact decimals, parser restrictions, and explicit user confirmation are preserved.

Large source inspections and preview DTOs use authenticated JSON metadata and ranges from their immutable DB stage; JSON is not uploaded as a generic file. Each response is at most 4MiB. Supabase preview creation returns only the new ID. Clients reconstruct the full DTO with its exact SHA rather than truncating cell values or lowering import limits.

AI assets retain the original 10MiB PDF/image limits and existing PDF/PNG/JPEG/WebP admission. WebP is restricted to the AI image purpose; it does not expand the general file allowlist. Parent-source reads resolve the exact input version, selected source, submission/request inclusion, frozen file hash, and current original/reference permissions before and after every remote chunk. Internal workers assemble bounded chunks; public routes require metadata plus Range/If-Match, and never expose signed download URLs. Standalone asset finalization does not create an AI input, submission, extraction, or model request.

Exports generate the existing workbook once, then conditionally create immutable private parts of at most 4MiB. A typed immutable `importExport` manifest stores ordered exact descriptors, total length and whole SHA. This supports workbooks larger than the bucket's 25MiB per-object limit without imposing a new export limit. Metadata and every range require the original actor and current product/internal-price authority. Cross-part ranges preserve ordering and the exact object versions. Manifest publication and exact audit are one transaction after a fresh authorization check. Existing SQL migrations are untouched; SQLite0018 and PostgreSQL0019 add manifest immutability.

Before writing export parts, a private server diagnostic records only the generated export UUID and allocated object UUIDs. Publication reports a bounded phase. An uncertain COMMIT response re-reads that exact manifest under fresh authorization, without generating another workbook. These diagnostics are best-effort operational evidence, not a durable orphan-recovery journal. Failed publication may retain unreferenced parts; no automatic final-object deletion is introduced. A new explicit export request generates a new snapshot of current data. Successful S1 uploads also retain staging duplicates under the previously documented S1 operating limitation.

The optional server-only `SUPABASE_STORAGE_NAMESPACE` supports isolated fixture deployments; its default is `gs-hale`. Transport construction remains lazy and strict. No token, Storage key, capability, descriptor or original bytes enter ordinary page or audit DTOs.

## Verification commands

- `npx vitest run tests/unit/imports-storage.test.ts tests/unit/storage-core.test.ts tests/unit/storage-supabase.test.ts tests/unit/imports.test.ts tests/unit/ai-input-server.test.ts tests/unit/postgres-foundation.test.ts tests/unit/repositories.test.ts`
- `node --conditions=react-server --import tsx scripts/verify-storage-excel-ai.ts <absolute-env-file> <new-private-report>`
- `node --conditions=react-server --import tsx scripts/verify-storage-excel-ai-webp.ts <absolute-env-file> <new-private-report>` after the main probe has created its synthetic export manifest.

The actual helpers use only a dedicated `gs_hale_storage_excel_ai_*`/`gs_hale_storage_excel_ai_ind_*` schema and a per-run UUID Storage namespace. They preserve schemas/DB rows, delete only their own generated remote keys, redact credentials, and make zero external AI provider calls. Service/runtime evidence does not substitute for the final two-server HTTP/browser checks or Vercel/Linux verification. Exact command/source bindings, original failures and scope corrections are stored in the private execution evidence.
